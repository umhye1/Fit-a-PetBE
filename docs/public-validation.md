# Fit a Pet 개선 검증 요약

인증 세션·데이터 접근 처리를 정리하고 게시글 조회에 커서 페이징을 적용했다. 백엔드 테스트 23건, 프론트엔드 테스트 12건과 양쪽 빌드가 통과했다. MySQL·Redis는 Testcontainers로 생성한 임시 환경에서 검증했다.

## 조회 성능 비교

합성 게시글 10,000건, 작성자 1명, 고정 seed 20261107의 카테고리 분포를 사용했다. 실행별 5초 워밍업 후 10 RPS로 20초간 200요청을 측정했고 조건별로 3회 반복했다. 앱 JVM heap은 256..512MiB, MySQL은 CPU 1·512MiB, Redis는 CPU 0.5·128MiB로 설정했다. 앱과 부하 발생기는 같은 호스트에 있다.

| 조회 방식과 실험 단계 | 회차별 p95 ms | p95 중앙값 ms | 응답 bytes |
| --- | --- | --- | --- |
| 전체 조회 후 필터 | 145 · 161 · 243 | 161 | 425,644 |
| DB 필터와 페이징 | 40 · 275 · 42 | 42 | 2,724 |
| 단일 조회 인덱스 추가 | 40 · 38 · 38 | 38 | 2,724 |
| 단일 조회 통계 갱신 | 48 · 49 · 61 | 49 | 2,724 |
| 키 선조회와 제한된 조인 | 41 · 44 · 175 | 44 | 2,724 |
| 최종 구현 통계 갱신 | 34 · 31 · 32 | 32 | 2,724 |

전체 조회와 최종 구현의 회차별 p95 중앙값은 161→32ms, 응답 크기는 425,644→2,724bytes다. 전체 목록을 최대 20건의 페이지로 바꾼 효과를 포함한다. 동일 응답 크기의 순수 SQL 개선율이나 운영 성능·최대 TPS 보장이 아니다.

인덱스와 통계 갱신만으로 API가 항상 개선되지는 않았다. 최종 구현은 키를 먼저 제한한 뒤 해당 건수만 작성자와 조회한다. 페이지당 SQL은 1개에서 2개로 늘지만 전체 자료를 읽는 비용을 제한하는 선택이다. 중간 단계의 지연 변동도 표에 포함했다.

수치는 각 200요청의 짧은 관측이며 고정 단계 순서, JIT·cache·호스트 잡음, 단일 작성자·합성 분포의 영향을 받는다. 운영 환경, 장시간 안정성, 10만·100만 건, 분리된 부하 발생기로 일반화하지 않는다. [측정값 집계](performance-summary.json)에 반복별 p50·p95·p99와 요청 수를 보관한다.

## 적용과 검증 범위

토큰 정책 변경에 따라 적용 시 재로그인이 필요하다. 프론트엔드는 변경된 인증·커서 페이지 응답 계약을 함께 반영한다. 기존 DB의 인덱스 적용은 배포 절차에서 확인해야 한다. 운영 DB 변경과 배포는 수행하지 않았다.

공개 문서는 변경 개요·집계 결과를 제공한다. 수정 전 보안 자료, 공격 재현 설명, 상세 인증 진단·보안 테스트 로그와 내부 경험 정리는 공개 커밋에 포함하지 않는다. 소스 코드와 정상적인 회귀 테스트는 저장소에서 확인할 수 있다.
